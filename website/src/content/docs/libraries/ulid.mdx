ULID (Universally Unique Lexicographically Sortable Identifier) is a 128-bit identifier spec: the top 48 bits are a millisecond timestamp, the remaining 80 are random. Cysharp's Ulid library is its C# implementation — a struct like `Guid`, allocation-free, with generation, parsing, and comparison all heavily optimized. In this project, `RoomId` and `MatchId` wrap it. The version is 1.4.1.

- GitHub: [Cysharp/Ulid](https://github.com/Cysharp/Ulid)
- Spec: [ulid/spec](https://github.com/ulid/spec)

## Why this library

A random `Guid` carries no information about when it was created, and sorting one yields no meaningful order. A ULID keeps its timestamp in the high bits, so sorting values is sorting by creation time — and the 26-character Crockford Base32 text form preserves that, so lexicographic order is chronological order too. For identifiers where "when was this created" is a natural question, as it is for rooms and matches, sorting a log by ID reproduces the sequence of events, and a DB index grows in insertion order.

## The two places that issue one

`RoomId` is issued by the matchmaking worker when it pairs two players:

```csharp
        var roomId = new RoomId(Ulid.NewUlid());
        var players = new[] { await SeatAsync(first), await SeatAsync(second) };

        var result = await roomControl.CreateRoomAsync(server.ControlEndpoint, new CreateRoomRequest(roomId, players));
```

`MatchId` is issued by the room, once per game. A rematch starts a new game in the same room, so it gets a fresh one:

```csharp
    // Identifies the game rather than the room: a rematch is settled on its own.
    public MatchId MatchId { get; private set; } = MatchId.New();
```

`MatchId.New()` is not hand-written. When the wrapped primitive is a `Guid` or a `Ulid`, [UnitGenerator](../unitgenerator/) also generates a static `New()` that mints a fresh value.

## One decision per boundary

Ulid is a third-party type, so every boundary the value crosses needs one decision about how to read and write it. Four boundaries appear in this project.

**The MessagePack wire.** The standard resolver doesn't know Ulid, so the formatter from the `Ulid.MessagePack` package is registered into the shared serialization options. When `RoomId`'s generated formatter serializes its inner value, it finds this formatter through the resolver. The registration code is on the [MessagePack-CSharp page](../messagepack/).

**The database.** `MatchId` is a key column of the match records, and Npgsql cannot map a Ulid. So this one type gets a hand-written converter instead of a generated one, storing the canonical 26-character text:

```csharp
[UnitOf(typeof(Ulid), UnitOptions.Transported | UnitGenerateOptions.ParseMethod)]
public readonly partial struct MatchId
{
#if NET10_0_OR_GREATER
    /// <summary>
    /// Stores the id as its canonical 26 character text. Written by hand rather than generated because
    /// UnitGenerator's converter would hand the provider a <see cref="Ulid"/>, which Npgsql cannot map.
    /// </summary>
    public sealed class MatchIdValueConverter()
        : ValueConverter<MatchId, string>(id => id.AsPrimitive().ToString(), text => Parse(text));
#endif
}
```

<SourceLink path="src/SharpCampus.Shared/Values/MatchId.cs" />

**JSON.** Ulid ships its `JsonConverter` only in the .NET build. That is why the Transported preset used by `RoomId` and `MatchId` drops JSON converter generation on netstandard2.1 and keeps it only in the net10.0 build the servers use — the same `#if` split in the preset you saw on the [UnitGenerator page](../unitgenerator/).

**Redis.** A matchmaking ticket sits in Redis as JSON text, so `RoomId` is stored as a string and turned back with `Parse` on the way out. The `Parse` and `TryParse` generated by the ParseMethod option carry this round trip:

```csharp
        var stored = JsonSerializer.Deserialize<StoredTicket>(value.ToString(), JsonSerializerOptions.Web)!;
        return new MatchTicket(RoomId.Parse(stored.RoomId), stored.Endpoint, stored.EntryToken);
```

The same 26 characters serve as the room routing key in the gRPC header and as the value you read with your own eyes in redis-cli. Having a human-readable, transcribable text form built into the spec turns out to be a quiet but real operational convenience.
