1부는 서버를 소스에서 실행했습니다. 이번에는 실제 배포 형태입니다. 컴포즈 파일 하나(<SourceLink path="deploy/docker/docker-compose.yml" />)가 메타게임 서버, 매치 서버 2대(`room-1`·`room-2`), 봇 서버를 이미지로 빌드하고, 그 앞에 Envoy 진입점을 두고, 스택 전용 Redis를 함께 띄웁니다.

Supabase만은 여전히 호스트의 스택입니다. 1부와 같은 명령으로 `supabase start`가 떠 있고 스키마가 적용된 상태여야 합니다.

## 1. 올리고 내리기

```bash
docker compose -f deploy/docker/docker-compose.yml up --build -d
docker compose -f deploy/docker/docker-compose.yml down
```

첫 빌드는 서버와 마스터데이터 데이터베이스를 이미지 안에 컴파일하므로 몇 분 걸립니다.

## 2. 클라이언트가 아는 포트는 하나뿐

클라이언트는 모든 것을 진입점 포트 5000으로 접근합니다. `SHARPCAMPUS_SERVER` 환경변수가 그 주소를 가리키게 합니다.

<Tabs>
  <TabItem label="PowerShell">
    ```powershell
    $env:SHARPCAMPUS_SERVER = 'http://localhost:5000'; dotnet run --project src/SharpCampus.Client
    ```
  </TabItem>
  <TabItem label="POSIX 셸">
    ```bash
    SHARPCAMPUS_SERVER=http://localhost:5000 dotnet run --project src/SharpCampus.Client
    ```
  </TabItem>
</Tabs>

`room-id` 헤더가 없는 gRPC 호출은 메타게임 서버로 갑니다. 듀얼 접속에는 헤더가 포함되고, Envoy가 그 방을 조회해 (메타게임 서버가 Redis를 근거로 답하는 내부 엔드포인트를 통해) 방을 소유한 매치 서버 인스턴스로 스트림을 라우팅합니다. 설정은 <SourceLink path="deploy/docker/envoy.yaml" />에 있습니다.

매치 서버는 호스트에 포트를 아예 공개하지 않습니다. REPL의 `status` 명령이 room 서버를 unreachable로 보고하는 것은 그래서이고, 정상입니다. 큐, 대전, 미션, 상점, 랭킹까지 나머지 전부는 5000 하나로 동작합니다.

## 3. 메트릭이 보고 싶다면

관측은 별도 프로파일입니다.

```bash
docker compose -f deploy/docker/docker-compose.yml --profile observability up -d
```

서버 4대의 메트릭 엔드포인트를 스크레이프하는 Prometheus가 [http://localhost:19090](http://localhost:19090) 에 뜹니다 (관례인 9090은 Windows가 예약하는 포트 범위에 들어 있어 피했습니다). 틱 소요 시간, 살아 있는 방 수, 큐 길이, 투입된 봇 수 같은 게임 자체 카운터도 함께 노출됩니다.

다음은 [3부: kind 위의 Kubernetes](../kubernetes/)입니다. 같은 이미지를 로컬 클러스터에 올리고, 롤링 업데이트가 진행 중인 매치를 어떻게 대하는지 확인합니다.
