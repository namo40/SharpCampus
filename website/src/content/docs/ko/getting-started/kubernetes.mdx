이번에는 [kind](https://kind.sigs.k8s.io/)로 로컬에 노드 3개로 구성된 클러스터를 만들고, 같은 이미지를 같은 Envoy 진입점 뒤에 그대로 올립니다. 이 구성은 완전히 자급자족입니다. PostgreSQL과 Supabase Auth(GoTrue)가 클러스터 안에서 서버들과 함께 실행되기 때문에, 앞의 1·2부와 달리 호스트의 `supabase start` 스택이 필요 없습니다.

오히려 떠 있으면 안 됩니다. 클러스터가 자체 인증 엔드포인트용으로 호스트 포트 54321을 차지하므로, 켜져 있다면 먼저 `supabase stop`으로 중지하세요. Docker Desktop은 이미지 빌드에만 쓰이고, 그 외에 필요한 것은 kind와 kubectl뿐입니다.

## 1. 클러스터 올리기

```bash
docker compose -f deploy/docker/docker-compose.yml build
kind create cluster --config deploy/k8s/kind-cluster.yaml
kind load docker-image sharpcampus-apiserver sharpcampus-roomserver sharpcampus-botserver --name sharpcampus
kubectl apply -f deploy/k8s/manifests/
kubectl create configmap sharpcampus-schema --from-file=schema.sql=deploy/db/schema.sql -n sharpcampus
kubectl get pods -n sharpcampus
```

클러스터 구성은 <SourceLink path="deploy/k8s/kind-cluster.yaml" />, 매니페스트는 `deploy/k8s/manifests/`에 있습니다. 게임 스키마는 여기서도 단일 파일 그대로라, `kubectl create configmap` 한 줄로 그 파일을 클러스터에 전달합니다. 데이터베이스 파드는 이 configmap을 기다렸다가 첫 부팅에서 스키마를 적용합니다.

모든 파드가 준비되면 대략 이렇게 보입니다. 매치 서버 2대가 StatefulSet(`room-0`·`room-1`)이 된 것이 컴포즈와의 차이입니다.

## 2. 접속은 그대로

클러스터가 진입점을 같은 호스트 포트에 매핑하므로, 클라이언트는 2부와 완전히 동일하게 `SHARPCAMPUS_SERVER=http://localhost:5000`으로 접속합니다. 회원가입과 로그인도 그대로입니다. 인증이 클라이언트가 이미 쓰는 호스트 포트(54321)에서 응답하기 때문입니다.

## 3. 이 구성의 하이라이트: 매치를 끊지 않는 롤링 업데이트

이 구성의 진가는 롤링 업데이트에서 드러납니다.

```bash
kubectl rollout restart statefulset/room -n sharpcampus
```

매치 서버가 1대씩 교체되는데, 교체되는 서버는 멈추는 대신 **드레이닝**합니다. 먼저 매치메이킹에서 빠지고, 진행 중인 듀얼을 끝까지 마친 뒤에야 내려갑니다. 그동안 새 매치는 다른 매치 서버에 계속 배정되므로, 롤링 업데이트가 진행 중인 매치를 끊는 일이 없습니다. 매치를 하나 진행해 둔 상태에서 재시작을 실행하면 직접 확인할 수 있습니다. 드레이닝 동작은 <SourceLink path="deploy/k8s/manifests/40-room.yaml" /> 매니페스트와 RoomServer의 종료 처리가 함께 만듭니다.

## 4. 정리

```bash
kind delete cluster --name sharpcampus
```

여기까지가 시작 가이드입니다. 이 스택이 왜 이렇게 나뉘어 있는지는 [아키텍처](../../architecture/)에서, 각 라이브러리가 코드 어디에서 쓰이는지는 [라이브러리](../../libraries/)에서 이어집니다.
